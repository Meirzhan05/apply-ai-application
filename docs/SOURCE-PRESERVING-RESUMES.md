# Source-preserving résumé layouts

PDF and DOCX source-preserving tailoring edits confirmed wording inside the uploaded document's existing layout. The uploaded file is context, not evidence: each factual claim still needs an explicitly confirmed profile fact tied to its source anchor. The renderer never adds a template, overlays white boxes, substitutes a fallback font, or removes original source content.

The source-preserving path accepts uploads up to 5 MB and up to 20,000 readable characters. It supports at most eight rendered pages and two text columns per page. PDF page count and regions are inspected at upload. DOCX pagination cannot be inferred from its XML, so the pinned LibreOffice renderer converts the untouched original before the writer receives page and region constraints; the actual page count is checked there. DOCX uses one section and the pinned Noto Sans runtime. Text that cannot be mapped unambiguously, unsupported page geometry, missing glyphs, or content that cannot stay within its original page region is blocked with an actionable error.

Baseline and tailored files must keep the same page count and page dimensions. Every source anchor stays on its original page and region, entries keep their employer or project association across page breaks, and repeated DOCX headers and footers must match on each rendered page. PDF source anchors retain their page and reading order. The worker checks the final output and stores its page count, per-page geometry, layout result, renderer metadata, and source/profile/facts/settings/job hashes with immutable, owner-scoped files. Preview, download, comparison, and browser attachment read the same saved PDF bytes.

An overlong edit may be shortened only within the existing preparation budget: at most three writer calls, four checker calls (including one malformed-checker retry), and two structural, factual, activity-preservation, or layout repairs combined. Layout feedback names the original page and region and is not a factual finding. Every rewrite receives the ordinary grounding check and a fresh layout render. If it still does not fit, the worker blocks the draft, reports an empty factual-finding list, and keeps the last valid packet available. Cancellation, authorization, the shared draft deadline, and usage metering apply to layout retries just as they do to factual repairs.

Existing valid one-page source artifacts retain their earlier validation policy and remain readable without rerendering. Structured LaTeX résumé drafting is a separate classic one-page flow; this eight-page bound applies to source-preserving PDF/DOCX tailoring.

## Feedback and repair

The writer returns only proposed edits to existing editable bullets. The application assembles all remaining claims from the inspected source and associates each with confirmed profile facts. Every candidate passes deterministic edit/evidence validation, the factual and original-activity audit, and rendered layout validation before it can replace saved materials.

Recoverable structural errors return precise feedback (the statement ID, failed rule, and permitted correction) to the writer. Factual exaggeration and substituted work activities also receive a repair opportunity when introduced by the writer. An unchanged original statement that cannot be established by confirmed evidence asks the user for information instead. Layout feedback targets one bullet; all other wording and evidence remain fixed. Each rewritten candidate repeats the checks. Identical rejected candidates and failures stop early instead of consuming the remaining repair budget.

One initial draft and two repairs share the existing deadline and run authorization checks. A malformed checker response receives one separate retry across the whole run, with no new writer call. Provider failures, unsupported source layouts, cancellation and changed run inputs stop the attempt. Preparation history records failed checks and recovery, and failure messages mention retained materials only when a previous packet actually exists.

New plans use evidence policy 3. Policy-2 plans remain readable with either complete anchor selection historically deployed under policy 2, including older separator/category claims. Evidence associations and same-entry constraints still apply; arbitrary incomplete manifests are rejected. The plan policy is included in saved file input hashes.

Run `npm run test:resume-feedback-worker` after deploying Trigger workers with a production `TRIGGER_SECRET_KEY`; the script rejects development keys before creating a run. It checks the deployed controller against generated PDF and DOCX sources and scripted model responses, including structural repair and malformed-checker recovery. It performs no paid model calls, profile or storage writes, browser actions, or employer submissions. This verifies controller behavior, not model quality on real applicants.
